# 미국 주식 OMS 실습 · 1~3강 (기존 학습 기록)

API·서버 개발 경험자를 위한 Python 프로젝트다. 첫 목표는 주문의 **의도를 저장하고, 중복 전송을 막고, 상태 변경을 설명할 수 있는 것**이다. 네트워크 호출과 API 키 없이 실행한다.

## 한 명령으로 OMS 시연

아래 실행 절차의 개발 의존성을 설치한 뒤 프로젝트 디렉터리에서 실행한다.

```bash
python -m oms.demo --output evidence/oms-demo.json
```

임시 DB에서 주문 중복 방지, 부분 체결과 체결 중복 방지, 전량 체결과 평균 체결가, 응답 유실 뒤 상태 대사·취소, 주문 한도 거절을 검증한다. 기존 실습 DB와 실행 중인 서버의 데이터를 변경하지 않는다. 모든 검증이 통과해야 결과가 저장된다. 이 시연은 로컬 모의 브로커를 사용하며 외부 증권사 연결이나 투자 전략의 성과 검증은 포함하지 않는다.

## 무엇을 만드는가

알고리즘 트레이딩 시스템은 보통 다음 흐름으로 나눠 생각할 수 있다.

```text
시장 데이터 → 전략 → 주문 의도 → OMS → 브로커
                                ↑       │
                                └ 접수·체결·취소 이벤트
```

전략은 “언제 무엇을 얼마나 사고팔 것인가”를 결정한다. OMS(Order Management System)는 그 주문이 접수됐는지, 중복인지, 취소됐는지 추적한다. 이번에는 이 경계를 먼저 만든다.

현재 지원 범위는 USD, 정수 주식, 지정가 매수, 주문당 학습용 한도, 접수, 조회, 취소, 상태 대사, 수동 모의 체결과 이벤트 이력이다. 종목 코드는 형식만 검사한다. 예시의 AAPL과 가격은 API 실습용 입력이며 현재 시세나 매수 제안이 아니다.

`SimBroker`는 별도 SQLite 파일에 접수와 취소를 기록하는 로컬 모의 브로커다. 2강에서는 상태 대사, 3강에서는 수동 체결·부분 체결을 추가했다. 시세 기반 자동 매칭, 현금·포지션, 매도, 장 운영 시간, 주문 만료, 인증은 아직 구현하지 않았다. 가격의 소수점 두 자리는 이번 실습의 단순화이며 미국 주식 전체의 가격 단위를 모델링한 규칙이 아니다.

## 실행

프로젝트 루트(최상위 README가 있는 디렉터리)에서 실행한다. 통합 프로젝트는 Python 3.12 이상을 사용한다.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m uvicorn oms.api:create_app --factory --host 127.0.0.1 --port 8000 --reload
```

[API 실습 화면](http://127.0.0.1:8000/docs)을 열어 `POST /orders`의 `Try it out`으로 다음 JSON을 보낸다.

```json
{
  "client_order_id": "lesson-001",
  "symbol": "AAPL",
  "side": "buy",
  "order_type": "limit",
  "quantity": 3,
  "limit_price": "100.25"
}
```

`Example Value`는 문서용 예시다. 실제 결과는 `Execute`를 누른 뒤 나타나는 **Server response → Response body**에서 확인한다. 아래쪽 Responses 표에 미리 표시된 예시와 구분한다.

실제 응답에서 `order_id`와 `status: "NEW"`를 확인한다. `NEW`는 브로커의 접수 응답을 받았다는 뜻이다. 주식을 샀다는 뜻은 아니다. 접수만으로 체결이 발생하지 않으며, 3강의 전용 API로 모의 체결을 기록한다. 위 요청의 `limit_price`는 실제 응답에서도 `"100.25"`다.

같은 JSON을 다시 보내면 동일한 `order_id`를 받는다. 같은 `client_order_id`로 수량을 4로 바꾸면 HTTP 409다. 새 주문 의도라면 새 `client_order_id`를 사용해야 한다.

그다음 `GET /orders/{order_id}/events`, `POST /orders/{order_id}/cancel`을 순서대로 실행한다. 취소 후 이벤트는 다음 순서다.

```text
PENDING_NEW → NEW → PENDING_CANCEL → CANCELED
```

`quantity: 101`을 새 ID로 보내면 `REJECTED`와 거절 사유가 저장된다. 기본 한도는 주문당 100주, 지정가 × 수량 10,000 USD다. 이 수치는 학습용 설정이며 계좌의 매수가능금액이나 적정 투자금이 아니다. 여러 주문을 합산한 노출 한도와 잔고 예약은 후속 과제다.

OMS 데이터는 `data/oms.sqlite3`, 모의 브로커 데이터는 `data/oms.broker.sqlite3`에 저장되어 서버를 재시작해도 유지된다. `OMS_DB_PATH`를 지정하면 브로커 파일은 그 파일 옆의 `<파일이름>.broker.sqlite3`을 사용한다. 두 파일은 독립 트랜잭션으로 저장한다. 보존할 주문이 있다면 DB를 지우지 않는다. 중복 방지 기록도 DB에 있다.

## 2강: 응답 유실과 상태 대사

코드를 수정하지 않고 전용 실험 API로 응답 유실을 재현할 수 있다. 일반 `POST /orders`는 정상적으로 동작한다.

1. `POST /simulation/orders/response-loss`에 아래 요청을 보낸다. 브로커가 먼저 접수 기록을 commit한 뒤 응답만 유실시킨다. OMS 응답은 HTTP 202, `PENDING_NEW`, `broker_order_id: null`이다.

```json
{
  "client_order_id": "reconcile-001",
  "symbol": "AAPL",
  "side": "buy",
  "order_type": "limit",
  "quantity": 1,
  "limit_price": "100.25"
}
```

2. `GET /simulation/broker-orders/{client_order_id}`에 `reconcile-001`을 넣는다. 브로커 쪽 기록은 `NEW`이며 브로커 주문 번호가 존재한다. 아직 OMS 기록은 `PENDING_NEW`다.
3. 1번 응답의 `order_id`로 `POST /orders/{order_id}/reconcile`을 실행한다. 브로커 기록을 조회하고 주문 내용과 비교한 뒤 OMS를 `NEW`로 갱신한다. 새 주문은 보내지 않는다.
4. 주문 이력을 조회하면 미확정 기록 뒤에 `NEW`와 대사 사유가 추가되어 있다. 브로커에 새 정보가 없으면 다시 대사해도 추가 상태 변경은 발생하지 않는다.

같은 실험을 반복하려면 새 `client_order_id`를 사용한다. 이미 처리한 ID는 새로 접수하지 않는다.

미확정 주문은 브로커 기록이 없거나 조회에 실패하면 HTTP 202와 미확정 상태를 유지한다. 조회 결과가 없다는 사실만으로 미접수라고 단정하거나 자동 재전송하지 않는다. 취소 미확정 주문은 브로커에서 `CANCELED`를 확인해야 취소 완료로 바꾼다. 여전히 `NEW`나 `PARTIALLY_FILLED`라면 체결 기록은 반영하되 `PENDING_CANCEL`을 유지한다. 전부 체결됐다면 `FILLED`로 확인한다. 이미 접수가 확인된 주문의 브로커 조회가 실패하면 HTTP 503과 함께 마지막 로컬 기록을 보존한다.

이전 스텁 버전에서 만든 주문 기록은 브로커 DB에 소급 생성하지 않는다. 특히 `raise BrokerUnavailable()`로 접수 전에 실패시킨 `timeout-001`에는 브로커 기록이 없으므로, 새 대사 기능을 호출해도 미확정 상태가 유지된다. 이번 실습에는 위와 같이 새 테스트 주문을 사용한다. 과거 스텁 주문의 취소도 브로커 기록이 없으면 확인할 수 없다.

## 3강: 체결과 부분 체결

1. `POST /orders`로 새 `client_order_id: "fills-001"`, AAPL 3주, 지정가 `"100.25"`인 주문을 넣는다. 응답은 `NEW`, `filled_quantity: 0`, `remaining_quantity: 3`이다.
2. `POST /simulation/broker-orders/{client_order_id}/fills`의 경로에 `fills-001`을 넣고 아래 체결을 기록한다.

```json
{
  "execution_id": "fills-001-exec-001",
  "quantity": 1,
  "fill_price": "100.00"
}
```

`quantity`는 이번 체결 한 건의 수량이다. 브로커 응답은 `PARTIALLY_FILLED`, 체결 1주, 미체결 2주다. 아직 OMS는 이전 상태를 보관한다.

3. OMS 주문 번호로 `POST /orders/{order_id}/reconcile`을 실행한다. OMS에도 체결 1주와 `PARTIALLY_FILLED`가 반영된다.
4. 동일한 체결 ID와 내용을 다시 보내면 HTTP 200이며 체결 수량은 증가하지 않는다. 같은 ID에 다른 내용이나 다른 주문을 붙이면 409다. 체결 ID는 이 단일 계좌의 모든 주문에 걸쳐 고유하다.
5. 두 번째 체결로 새 ID `fills-001-exec-002`, 수량 2주, 가격 `"99.50"`을 기록한 뒤 대사한다. 체결 3주, 미체결 0주, `FILLED`로 바뀐다. `GET /orders/{order_id}/fills`에서 개별 체결 기록을 확인한다.

주문 수량은 유지하며, `주문 수량 = 체결 수량 + 미체결 수량`을 지킨다. 평균 체결가는 `체결 금액 합계 ÷ 체결 수량`으로 계산한다. 예시에서는 `(1 × 100.00 + 2 × 99.50) ÷ 3 = 99.6667`이다. 내부 금액은 정수 센트로 합산하고 평균만 소수점 네 자리에서 반올림해 표시한다.

잔량을 초과하거나 매수 지정가보다 높은 가격으로 체결을 만들면 409다. 부분 체결 후 취소하면 이미 체결된 수량과 체결가는 보존되고, 나머지 수량에 대한 실행이 중단된다. 이때 `remaining_quantity`는 아직 체결되지 않은 수량을 나타내므로 `CANCELED`에서도 0보다 클 수 있다. 전부 체결되거나 취소된 주문에는 새 체결을 추가하지 않는다. 기존 체결 ID의 동일한 재요청은 종료 후에도 중복 반영 없이 반환한다.

체결 원장과 상태·이력 갱신은 OMS의 한 트랜잭션으로 저장한다. 브로커 DB에서는 체결 기록과 상태를 함께 저장한다. 주문 요청을 다시 보내는 것으로 체결을 만들지 않는다. 브로커와 OMS의 체결 목록은 대사를 거쳐 맞춘다. 오래된 브로커 조회 결과로 이미 반영한 체결을 줄이지 않는다.

기존 주문과 브로커 기록은 스키마 확장 후에도 보존된다. 현금 차감, 포지션 원장, 수수료, 체결 정정·취소는 다음 단계의 범위다.

### 1. 금액은 어떻게 다루는가

API에서 `"100.25"`라는 문자열을 받고 Python에서는 `Decimal`, DB에서는 정수 센트 `10025`를 쓴다. `float`의 이진 소수 오차를 금액 계산과 중복 비교에 끌어들이지 않기 위해서다. 수량도 정수만 허용한다.

### 2. 왜 client_order_id가 필요한가

HTTP 타임아웃은 “서버가 처리하지 않았다”는 뜻이 아니다. 요청은 처리됐지만 응답만 유실됐을 수 있다. 같은 의도의 재시도에 같은 ID를 사용하면 기존 기록을 조회할 수 있다. 이 실습의 단일 계좌 범위에서 DB의 `UNIQUE` 제약과 짧은 트랜잭션이 동시 중복 생성을 막는다.

동일한 ID와 정규화된 내용은 기존 주문을 반환한다. 같은 ID에 다른 종목·수량·가격을 붙이면 409다. 취소·거절된 주문의 ID도 재사용하지 않는다. 다중 계좌를 도입하면 ID의 고유 범위도 계좌를 포함하도록 설계해야 한다.

### 3. 왜 브로커 호출 전에 저장하는가

`OrderService.submit()`에서 다음 순서를 확인한다.

```text
① PENDING_NEW와 최초 이벤트를 DB에 저장하고 commit
② DB 트랜잭션 밖에서 broker.submit(order) 호출
③ 접수 응답을 받으면 NEW와 broker_order_id를 함께 저장
```

브로커가 접수했는데 ③ 전에 프로세스가 종료되면 로컬에는 `PENDING_NEW`가 남는다. ① 직후, 실제 전송 전에 종료돼도 같은 상태다. 따라서 **로컬 상태만으로는 브로커의 주문 존재 여부를 확정할 수 없다.**

`BrokerUnavailable`은 이 불확실성을 나타낸다. `REJECTED`로 바꾸거나 새 주문을 자동 전송하지 않고, 미확정 상태와 사유를 보존한다. 반면 `BrokerRejected`는 명시적인 거절 응답을 받았다는 뜻이다. 브로커 어댑터가 이 예외를 올바르게 구분해야 한다.

같은 주문 요청을 재시도해도 보존된 주문만 반환하므로 브로커로 다시 전송되지 않는다. 2강에서 추가한 수동 대사는 원래 클라이언트 주문 ID로 브로커를 조회하고, 내용과 확인된 상태를 OMS에 반영한다. 조회 실패나 기록 없음은 미확정으로 남기며 자동 재전송하지 않는다. 이는 분산 시스템의 exactly-once 실행을 보장하지 않는다. 실제 어댑터에서도 최초 전송과 조회에 같은 클라이언트 주문 ID를 사용해야 한다.

### 4. 취소도 확인이 필요한가

취소 의도를 저장한 `PENDING_CANCEL`과 취소 확인을 받은 `CANCELED`를 구분한다. 응답이 유실되면 `PENDING_CANCEL`을 유지한다. 취소 응답 뒤에는 브로커 기록을 조회해 최신 체결과 상태를 함께 반영한다. 명시적 취소 거절도 조회 결과를 확인한 뒤 `NEW`, `PARTIALLY_FILLED` 또는 `FILLED`로 반영한다. 이미 체결된 수량을 취소로 되돌리지 않는다.

상태 변경과 그 이벤트는 한 트랜잭션에 저장한다. `UPDATE ... WHERE status = ?`를 사용해 이미 바뀐 상태를 오래된 요청이 덮어쓰지 않게 한다. 동시에 들어온 취소 요청 중 상태 변경에 실패한 요청은 409를 받을 수 있으므로 다시 조회한다.

### HTTP와 주문 상태는 다른 층위다

| HTTP | 의미 |
| --- | --- |
| 201 | 새 주문 기록 생성. 업무상 거절 기록도 포함하므로 `status`, `reason`을 확인 |
| 200 | 기존 주문 반환, 조회 또는 확정된 취소 처리 |
| 202 | 신규 접수 또는 취소가 미확정. 브로커 성공 여부를 뜻하지 않음 |
| 409 | 같은 ID에 다른 내용 또는 현재 상태와 충돌 |
| 422 | 입력 오류 또는 아직 지원하지 않는 주문 조건 |
| 404 | 주문 기록 없음 |
| 503 | 접수가 확인된 주문의 브로커 조회 실패. 마지막 로컬 기록 보존 |

## 테스트와 첫 과제

```bash
python -m pytest -q
```

테스트는 임시 DB를 사용한다. 응답 유실 테스트는 **브로커가 접수한 뒤 응답을 잃어버리는 상황**을 주입한다. 동시 요청 테스트에서는 같은 의도 16건이 주문 1건과 브로커 호출 1번으로 끝나는지 검사한다.

직접 해볼 과제:

1. `max_quantity`를 100에서 50으로 바꾸고 한도 거절 테스트의 결과를 예상한다.
2. 같은 ID로 같은 주문, 다른 가격 주문을 각각 보내 응답 차이를 확인한다.
3. `test_order_is_committed_before_broker_call_and_timeout_does_not_resubmit`을 읽고, 타임아웃을 `REJECTED`로 기록하면 어떤 잘못된 판단을 유발할지 설명한다.

## 다음 순서

1. 현금·포지션 원장과 주문 예약: 중복 매수 여력 사용 방지, 매도 가능 수량.
2. 시세와 단순 전략: 동일 전략을 재생 데이터와 로컬 시뮬레이터에 연결.
3. 백테스트: 수수료·슬리피지·미래 데이터 참조 오류를 포함한 검증.
4. 브로커 paper API 어댑터: 계좌 조건 확인, 스트리밍 이벤트, 로컬에서 익힌 대사 흐름과 장애 복구 정책 적용.

브로커는 아직 선택하지 않았다. 외부 paper 계좌 연결 단계에서 거주지·계좌 지원 여부와 사용할 API를 확인한다.

참고: [Alpaca 주문 문서](https://docs.alpaca.markets/us/docs/orders-at-alpaca)는 클라이언트 주문 ID와 실제 주문 생명주기의 예를 제공한다. [FastAPI 테스트 문서](https://fastapi.tiangolo.com/tutorial/testing/)는 이 프로젝트의 `TestClient` 사용 방식에 대한 공식 설명이다. 실제 브로커 상태 전체를 이번 모델이 구현하는 것은 아니다.
